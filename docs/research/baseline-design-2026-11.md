# 足球横转竖：Baseline 调研与实验设计

核验日期：2026-11-14。范围：2024–2026 年的通用视频理解、视觉跟踪与视频重构；补充与任务直接相关的较早工作。本文是设计，不是实验结果。官方模型能力、论文结论与本项目假设分别陈述；不把通用 benchmark 的领先等同于足球裁切 SOTA。

## 1. 先明确要验证的产品能力

输入一段约 30 分钟的连续足球转播，系统自行发现有价值的事件，决定每个阶段应该展示什么，输出 9:16 片段。不能预设永远跟球或同一个人：射门前可能需要球与接球队员，射门时需要球与球门，随后可能需要庆祝者；回放则有不同节奏。

核心问题是：在相同成片质量下，Drex 的决策、工具调用与记忆管理，能否减少总成本或出片时间？更少检测调用本身不代表成功。

建议分两层评测：

| 层次 | 统一输入 | 比较内容 | 能回答什么 |
|---|---|---|---|
| A：片段裁切 | 人工选定的同一连续片段；不提供目标人物或球的坐标 | 自主选择关注对象、裁切路径、保持连续性 | 谁真正裁得好，成本如何 |
| B：完整任务 | 同一约 30 分钟转播与音轨，无高光时间提示 | 事件发现、去重、片段边界、裁切与成片 | 哪套系统更适合产品 |

另有可选感知诊断：给所有 tracker 同样的首帧框，单测跟踪。这属于辅助实验，不是“不主动指定目标”的主任务。

## 2. 最近工作的核验结果

### Gemini：必须保留原生视频强基线

截至核验日，官方列出稳定模型 `gemini-4-hydrogen`（2026-11 更新），支持视频/音频输入、结构化文本输出及 agentic video；`gemini-3.8-flash` 是仍可选的稳定 Flash 模型。优先使用 Hydrogen；若账号不可用则明确记录改用 3.8，不能静默替换。文档可用性尚不等于本账号调用成功。[Hydrogen 模型页](https://aistudio.google.com/docs/models/gemini-4-hydrogen)、[3.8 Flash 模型页](https://aistudio.google.com/docs/models/gemini-3.8-flash)。

官方视频接口有 static 和 agentic 两种模式：默认静态采样为 1 FPS；agentic 模式可自主查看时间线、转录及不同帧率/分辨率的片段。通过视频输入的 `processing: "agentic"` 启用，并可从响应步骤核对实际使用情况。这与本项目“按需观察”的思路直接相关，不能只比较固定低帧率 Gemini。对于快速传球，默认采样遗漏细节是待测风险；自适应模式也不保证精确定位小球。[视频接口](https://aistudio.google.com/docs/video-understanding)。

本项目需要的是裁切计划 JSON，再由 FFmpeg 等工具生成成片；模型支持视频输入不等于直接输出已裁切视频。原生视频对照适合验证“通用模型能否直接完成导演任务”，同构替换对照则用于隔离 Drex 决策的贡献。

### Qwen3-VL：可选的开放权重对照

2025 年 Qwen3-VL 提供视频理解、时间定位和二维 grounding，包含 8B、32B 等规模；技术报告描述原生 256K 上下文与文本时间戳对齐。可以用 `Qwen3-VL-8B-Instruct` 做部署探索，32B 做更强档位，但不应将小模型结果称为开放模型能力上限。输入采样、显存与推理速度需要单独测量；ASR 转录可作为附加文本统一提供，不能假设该 VL 接口原生理解音频。[官方仓库](https://github.com/QwenLM/Qwen3-VL)、[技术报告](https://arxiv.org/abs/2511.21631)。

第一轮不优先引入：本地推理部署会增加变量，也不能把 GPU 推理成本记成零。

### SAM 与检测跟踪：强感知不等于导演

SAM 2/2.1（2024）、SAMURAI（2024）、SAM2Long（2025）、SAM 3（2025）及 SAM 3.1（2026）的能力、限制和源链接见 [视觉跟踪专项调研](visual-tracking-baselines-2026-11.md)。建议第二阶段使用 SAM 3.1；如模型访问或硬件不满足，显式另设 SAM 2.1 对照，不混报名称。

这类模型擅长保持对象或分割，但“球员”概念检测并不回答应该跟哪个人，也不回答何时从射门切到庆祝。公平设计必须明确目标选择模块，并计入其成本。SAM2Long 原版最终路径利用整段信息，归入离线比较。

实用轻量方案采用 YOLO26 + 显式配置的 BoT-SORT 或 ByteTrack；版本新不证明足球小球表现好。ByteTrack 本身是较早方法，定位为成熟关联器，不包装成 2026 新模型。足球专用训练/权重和通用权重应分开报告，不能只拿失效的通用小球检测制造弱对手。

### SmartCrop：任务最接近的既有方案

SmartCrop 的足球版本采用对象检测、场景检测、异常点处理与插值来选择裁切中心，并评估 16:9 到 1:1 / 9:16 的观看体验；2024 年继续有足球及体育视频裁切工作。这是应该复用其思路的直接参考。[ISM 原论文](https://doi.org/10.1109/ISM59092.2023.00009)、[MMM 2024 作者稿](https://oda.oslomet.no/oda-xmlui/bitstream/handle/11250/3164019/2024_mmm_demo_smartcrop.pdf?isAllowed=y&sequence=4)、[体育裁切作者稿](https://munin.uit.no/bitstream/handle/10037/36766/article.pdf?isAllowed=y&sequence=4)。

如果我们以新 detector 重建其关键思路，应命名 `smartcrop-inspired`，不能声称复现了原论文或直接搬用原论文分数。

### 2026 年直接裁切研究：帮助设计候选与评价

LIVE-YT VC / VC++ 研究提供人类主观竖屏裁切标注及时间平滑标注，提示合理裁切可能不唯一；这支持我们标注可接受区域和观看偏好，而不只比较与单一框的 IoU。[2026-04 论文](https://arxiv.org/abs/2604.24947)。

BayesCrop 是 2026-11-06 的新预印本，研究多种合理裁切位置的概率表达，以及稀疏锚帧预测配合压缩视频运动向量传播。与我们的候选窗口和轻量传播相关，但尚未在本项目核验代码、权重及足球表现，先作为设计参考，不列为立即可跑的基线。[论文](https://arxiv.org/abs/2611.09100)。

## 3. 推荐基线矩阵

| ID | 方案 | 目标选择 / 记忆 / 工具 | 主要回答的问题 | 顺序 |
|---|---|---|---|---|
| B0 | 固定中心 9:16 裁切 | 无模型、无语义记忆 | 最低成本参照、指标是否会奖励不动的错误画面 | 第一轮 |
| B1 | Gemini 原生视频导演 | 视频+音轨；输出事件与裁切计划；static、agentic 分开跑 | 直接给通用视频模型是否足够 | 第一轮 |
| B2 | Gemini 同构替换 | 与 Drex 相同帧、网格/候选、记忆快照、工具权限、恢复模块 | 收益是否来自 Drex 模型 | 第一轮 |
| B3 | SmartCrop-inspired 视觉方案 | YOLO26 + BoT-SORT；规则选择焦点；轨迹状态；镜头内平滑 | 成熟视觉方案是否已经够好 | 第一轮 |
| B4 | 强感知混合方案 | 与被比较系统相同导演 + SAM 3.1 持续跟踪 | 按需重定位能否替代持续重型视觉 | 第二轮 |
| B5 | Qwen3-VL | 同构决策，或视频输入+公共 ASR | 开放权重模型的质量/成本位置 | 可选 |
| D-fixed | 仓库已有 Drex 固定采样原型 | 每 0.5 秒关键帧；8 帧一批；栅格边界 choice；按镜头平滑 | agent 自适应调度的参照 | 第一轮 |
| D-agent | 待实现 Drex agent | 编辑、导演、复核职责；工具按需调用；共享证据与状态 | 项目完整假设 | 第一轮后迭代 |

B4 的持续版本与按需版本应保持同一导演和恢复能力，改变调用策略即可。若另用 Gemini 做 B4 的导演，则将其列为独立混合产品方案，不能用它单独归因“检测频率”的作用。

## 4. 各基线的具体实现合同

### B1：Gemini 原生视频导演

**A 层：** 输入同一片段，提示模型识别事件阶段并输出裁切锚点、关注对象、必须保留内容和不确定性。第一版每 0.5 秒一个锚点；输出通过公共路径规划器插值与平滑。该时间间隔是实验初值，不是已验证最优值。

**B 层：** 首次输入完整约 30 分钟视频，自行返回事件候选与证据时间戳；再输入选中片段生成空间裁切计划。两轮全部计费。这样避免用一次长视频回答强行产生几千个高精度坐标。另可保留单次调用版本作便宜档位，不能混为同一配置。

同一模型分别跑 static 与 agentic；先以官方默认 static 配置建立可复现参照，再在开发集上检查更密采样的质量/成本收益。记录实际模式、采样、分辨率、模型 ID、请求与响应元数据。不把静态 1 FPS 的失败作为 Gemini 能力上限。

片段内输出合同示意（项目自定义，不是厂商 API 原生 schema）：

```json
{
  "event_id": "e01",
  "timebase": "source_video_seconds",
  "start_s": 4450.0,
  "end_s": 4480.0,
  "anchors": [
    {
      "t_s": 4451.0,
      "focus": "ball_and_receiver",
      "must_keep_xyxy": [0.31, 0.24, 0.58, 0.88],
      "evidence_t_s": [4450.5, 4451.0],
      "action": "crop",
      "uncertain": false
    }
  ]
}
```

坐标为相对源画面的 [0,1]；所有时间均为源视频播放时间。验证器检查框顺序、边界、时间单调、片段范围与缺失锚点。格式修复和重试都计入成本。不可将模型自述置信度直接作为校准过的概率。

### B2：Gemini 同构决策器

第一版针对当前仓库的 `s3`：固定同一批 8 帧、16×9 栅格、问题及标签，Gemini 输出与 Drex 对应的景别和四个边界编号；其他步骤共用。先用相同的非置信度加权平滑，避免把 Drex 的类别概率与 Gemini 自报信心混用。Drex 原生概率加权另做消融。

未来针对 D-agent：每个决策点使用当前全景 1 张、前一时刻全景 1 张、焦点参考图 1 张、候选裁切 5 张，共 8 张；参考图缺失采用明确缺失标记。候选坐标由程序生成、编号固定，两种模型都可选某个编号、保持、重定位或请求额外证据。候选数和具体布局需开发集验证。

需要区分两种测法：

- 固定观察日志回放：两模型看完全相同的图像与记忆，测单次决策质量。不会产生可比较的完整闭环轨迹。
- 闭环运行：工具权限、预算、初始状态与候选生成算法相同，后续状态允许因决策而分岔。最终以成片与全成本比较，不能声称所有中间图片都相同。

### B3：视觉规则导演

基础链路：公共镜头切分 → player/ball detector → 显式 BoT-SORT 跟踪 → 规则焦点 → 公共裁切规划器。

建议初始规则：活跃比赛且球可靠可见时，关注球与最近相关球员；球暂失时短时轨迹预测并降低信任，随后回退到场上运动区域或保守构图；特写时选主要人物；镜头切换清空运动轨迹，重新检测。仅凭球与球员距离并不能可靠判断控球，应记录这一局限。回放是时间叙事属性，不能只凭单帧景别决定。

保留逐帧检测作为完整计算参照，另设 5 Hz 检测、跟踪/裁切输出随视频帧率的成本变体；这是参数初值，不预设实时性。规则自适应版本根据预测出框、轨迹残差、失配和镜头切换触发额外检测，用于验证“简单调度已经足够”的假设。

B 层可使用公共 ASR 的关键词/音量事件召回形成明确的 `B3+rule-events`。同时给 B3 运行 A 层的人工事件窗口，避免事件召回失败掩盖裁切能力。SCRFD 人脸检测不适合充当足球远景的主要定位模块。

### D-agent：被测系统的角色与可观测状态

角色是权限与职责边界，不要求每个角色都另开昂贵模型会话。

| 角色 | 决策权 | 可调用工具 | 保存的记忆 |
|---|---|---|---|
| 编辑 | 哪个事件值得成片、事件起止、原直播与回放是否重复 | 转录检索、音量峰值、时间线抽帧、片段查看 | 事件账本：时间、证据、候选类别、重复关系、未知项 |
| 导演 | 当前应该展示什么、保持/移动/换焦点/请求定位 | 栅格、候选窗口、运动预测、检测/分割、局部放大 | 工作状态：当前镜头、焦点、上一裁切、速度、参考图、目标最后可见时间 |
| 复核 | 是否缺关键动作、是否抖动，批准或指定有限修订 | 成片预览、关键时刻对照、路径诊断 | 失败记录：证据时间、失败类型、修订次数与预算 |

所有记忆条目带来源时间、可用时间、可靠性和过期条件。切镜头清空坐标/速度等局部状态，事件语义可保留；旧参考图不能当成新镜头中仍然可见的证据。限制复核最多一次修订作为初始预算，记录实际调用，防止无限返工。

消融按优先级做：固定频率 vs 规则触发 vs Drex 触发；随后比较是否有事件记忆、是否有复核。一次只移除一种机制。NDI/Whisper 在此作为转录工具，既不默认提供视频对象跟踪，也不把解说当作视觉真值。[已核验接口说明](soccer-reframe-api.md)。

## 5. 公共裁切与平滑规则

第一轮固定源画面高度，9:16 裁切只移动水平中心；在 16:9 输入上约保留 31.6% 的横向宽度。这样先隔离“看哪里”，之后再统一开放缩放。模型请求的必须保留区域如果横跨更大范围，应标注为不可同时容纳，而不是悄悄丢掉一侧。

分两个输出任务：主榜为纯 9:16 crop；产品扩展允许在不可容纳时用完整横画面置于竖屏画布，单独统计回退比例与主体可读性。不能让总是缩成小横屏的系统靠高保留率取胜。

所有受控对照共用规划器、输出分辨率、编码参数、速度/加速度限制与最短焦点保持时间。原视频切镜处允许硬切，不跨无关镜头强行平滑；同镜头突然跳变才主要计为额外抖动。离线可使用前后文及整段优化，直播版本只能使用已到达帧，另列实测前瞻/缓冲延时。

关注“源坐标中的裁切移动”和“输出中主体运动”两类指标：源转播自身会摇镜，裁切路径平滑并不自动等于观看平稳。

## 6. 利用现有素材做第一轮实验

素材：

- 开发：`samples/football-keyframes/videos/el-clasico-2017.mp4`，源播放 4350–6150 秒。
- 暂定保留测试：`samples/football-keyframes/videos/belgium-japan-2018.mp4`，4200–6030 秒。

两场都是知名比赛，模型可能记得赛果。提示不提供事件答案、不联网检索比赛事实，要求附当前输入的可见/可听证据。由于我们此前已经看过两场抽帧，这只是开发阶段留出，并非严格从未接触的盲测；未来需要第三场未使用比赛检验泛化。

第一步使用现有 30 张图片检查网格映射、空间输出格式与明显漏裁，不能用于宣称平滑性、跟踪稳定性或事件识别成绩。

第二步从连续视频建立 12–20 个 20–60 秒片段，前后保留上下文。至少覆盖：普通远景、快速转移/长传、带球突破、射门与球门空间分离、遮挡、球暂失、进球后庆祝、原直播转回放、特写转远景。片段数取决于原素材实际覆盖；没有的场景不制造标签。保留普通无事件片段作为负例，避免只评估容易的进球。

第三步完整约 30 分钟事件发现。统一输出最多 5 个不重复事件、总时长预算 180 秒作为初始产品条件；不能输出越多越长就得到更高召回。

标注由人复核：事件类别/起止/峰值/回放关联、关键时刻必须可见的对象或区域、允许的焦点切换、合理裁切中心区间、不可单一竖框容纳的时刻。至少两人对成片做匿名随机顺序偏好评价；有分歧的裁切保留多个可接受答案。SAM、Gemini、Drex 的结果均不能直接成为真值。

## 7. 指标与记录

| 维度 | 主要指标 | 注意事项 |
|---|---|---|
| 事件 | 事件级 precision/recall、峰值时间误差、片段完整性、重复率 | 开始前固定事件匹配容差；直播/回放不可算两次新进球 |
| 内容 | 关键对象保留率、必须保留区域覆盖、错误焦点时间占比 | 对进球瞬间等关键时刻单独报；按可容纳/不可容纳分组 |
| 跟踪 | 错跟次数、丢失时长、恢复时间 | 跨镜头与镜头内区分；人工确认身份，不只比较 tracker ID |
| 构图 | 主体大小、球/球门可读性、无效缩放/回退比例 | 不能只优化中心误差或把所有内容缩小保留 |
| 连续性 | 同镜头裁切速度/加速度、额外跳变率、主体画面运动、盲评舒适度 | 结合关键内容保留率，固定中心不能凭零运动成为赢家 |
| 延时 | 冷启动/上传/首个可用片段/全部完成时间、实时倍率 | 原生 agentic 的内部观察也可能增加延时 |
| 成本 | 每输入分钟与每有效输出分钟总成本 | 同时报质量，不把失败造成少输出当节省 |

总成本 = 模型输入/输出/思考/工具使用费用 + ASR + detector/segmenter GPU 时间 + 帧处理与编码 + 存储/网络等实际费用。根据当日价格和实际 usage 计算，避免 token 子项重复计费；缓存命中、重试、失败与人工修订时间单列。Gemini 和 Drex 的 token 口径不应直接当成同一种单位。[Gemini 价格页](https://aistudio.google.com/docs/pricing)。

每次 run 保存：源文件哈希、时间窗口、分辨率、模型及权重版本、代码提交/工作区快照、prompt 版本、随机参数、采样策略、工具调用日志、记忆快照摘要、实际 usage、重试、时间与输出。缓存按输入和配置签名区分，不能只按 s3.json 文件名复用不同模型的结果。

第一轮各配置运行一次找接口与指标问题；正式小样对生成式配置重复三次，报告逐片段差值和分布。两场比赛无法支持“普遍 SOTA”的结论；用质量—成本图选择可行配置，不人为构造一个加权总分掩盖漏掉进球。

## 8. 与现有代码的衔接和实施次序

当前仓库已有 `reframe/pipeline.py`、`grid.py`、`smooth.py` 和网格实验。它采用固定频率与整段平滑；此次只做研究设计，没有修改执行代码，也没有运行新的付费模型基线。

建议按以下顺序落地：

1. 为当前 `D-fixed` 固定配置，建立公共结果 schema、运行签名和指标；完成小片段人工标注。
2. 接入 B0、B1 原生视频两种模式、B2 Gemini 栅格同构替换。这一步最快回答通用模型是否已经足够。
3. 实现 B3 的常规视觉与规则自适应版本，检查小球检测质量；检测器失效时先修数据/权重，不急于宣布 Drex 胜出。
4. 在同一工具与输出接口上实现 D-agent，比较固定、规则、模型调度；再加入 SAM 3.1 强感知对照。
5. 按需扩展 Qwen3-VL、缩放/横屏保留策略与第三场未见比赛。直播评测单开配置，不沿用离线未来帧。

第一轮的成功条件是找到一个可复核的改进：例如关键动作保留与观看偏好相当时，全成本更低；或成本相近时明显减少关键漏裁。当前没有数据证明哪一套更便宜、更快或更准确。
